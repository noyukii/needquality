# Changelog

Read this when they said changelog, release notes, or CHANGELOG.
Describe the named git range for its users. Do not implement a feature.

1. Read the range and the repo's existing release-note format.
2. Group only user-visible changes. Name breaking changes, migrations,
   and known limitations; omit internal churn and invented impact.
3. Match the file's heading and tense. Keep links, issue numbers, and
   contributor names only when present in the range.

Don't: write a future roadmap, fabricate metrics, or create a second
summary file when the repo already has a changelog.
